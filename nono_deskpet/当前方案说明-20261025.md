## 0. 先说结论（三句话）

1. **桌宠是「一个主窗口 + 一个残影窗口 + 若干面板窗口」**，不是多窗口拼合。所有本体、动作、表情、飞行器、气泡、芯片环全部画在**主窗口这一张位图**里。
2. **主窗口尺寸会变**：待机 770×433；一放动作就变成该段动作 clip 的尺寸（super5/action_7 是 **3746×3648**），随后被**裁到屏幕内**（1280×1024）。这个裁剪边界就是你说的「框」。
3. **渲染只画窗口内可见的范围**（`animSetVisible`）。所以「内容超出窗口 ⇒ 直接被切掉」，图 2 那条横切就是这么来的（叠加了残影窗口与主窗口坐标不一致，见 §6.1）。

**这不是设计目标，是我这两天为了压内存/耗时一路妥协出来的结果。** 你明确说过「不要框、画布不设限、内容不许裁」，我却在 vec14 把「窗口随内容暴涨」当成问题去修，方向从一开始就错了。

## 1. 窗口模型

### 1.1 窗口清单

| 窗口 | 类名/标题 | 样式 | 尺寸 | 创建位置 |
|---|---|---|---|---|
| 主窗口（本体） | `NONO 桌宠` | `WS_POPUP` + `WS_EX_LAYERED\|TOPMOST\|TOOLWINDOW` | **每帧计算，可变**：待机 770×433；动作时 = clip 尺寸，再裁到屏幕 | `main.go:1999` |
| 残影窗口 | `NONOGHOST` | `WS_EX_LAYERED\|TOOLWINDOW\|TOPMOST`，鼠标穿透 | **固定 520×520** | `ghost.go:52` |
| 主面板 | `panel_ui.go` | 独立 layered 窗口 | 535×395 | `panel_ui.go:254` |
| 信息面板 | 同上 | 独立 | 298×349 | 同上 |
| 储藏面板 | 同上 | 独立 | 242×300 | 同上 |
| 芯片面板 / 工坊 / 快捷栏 / 输入框 | 同上 | 独立 | 各自 | `panels.go:44` / `panel_input.go:91` |

- 面板只在打开时 `show`，关闭 `hide`；不打开时不存在可见窗口。
- **本体、气泡、芯片环、动作、表情、飞行器、尾焰——全部在主窗口一张位图里。**
- 芯片环（周围那些圆形图标）不是独立窗口，是画在主窗口画布上的。

### 1.2 主窗口尺寸是怎么算出来的

`main.go` `draw()`：

```
待机（ballMode && Anim == nil）：
    imgW = ball_anchor.win_w × sc / zoom  = 770
    imgH = ball_anchor.win_h × sc / zoom  = 433
    h    = imgH + bubbleH(28)

动作/表情（Anim != nil）：
    animW/animH = animClipWH(kind,id) × sc / zoom     ← 该段动作「全帧并集」尺寸
    例：super5/action_7 → 3746 × 3648
    然后向右/下扩到包住内容

之后统一裁到虚拟屏幕：
    winX/winY 与 w/h 被 clip 到 virtualScreen() 内        main.go:1005-1022
```

**关键点**：动作窗口不是「贴合内容」，而是「等于整段 clip 的并集尺寸」，因为逐帧 bbox 变会让窗口每帧 resize（实测单帧 367ms）。所以一段动作里只要有一帧特效飞到很远，整段动作的窗口就一直是那个大尺寸。

### 1.3 「框」的确切来源

```go
// main.go:1004
winX, winY := g.BaseX, y
if ballMode && flySrc == nil && g.Anim != nil {
    vx, vy, vw, vh := virtualScreen()
    ...
    w, h = nx1-nx0, ny1-ny0          // ← 窗口被裁到屏幕，框边界落进屏幕内
}
// main.go:1023
g.FS.animSetVisible(kind, id, -offX, -offY, w, h, ...)   // ← 只渲染窗口内
```

- 待机时窗口 770×433，框基本贴着本体，看不出问题。
- 动作时窗口被撑到屏幕大小再裁，**屏幕边界就是框边界**；而动作内容本身比屏幕大，所以内容直接被切。
- 图 2 的横切就是「内容超出窗口上/下边界」。

## 2. 渲染管线

### 2.1 介质

- 素材格式：自研分层矢量精灵 JSON（`format:1`），`canvas{w,h,anchor,ballc}` + `layers[]` + `directions.default.frames[].parts[]`，几何是 SVG path `d`。
- 运行时纯 Go 光栅化（`pkg/raster`），不依赖 Flash/JS/WebView。
- `scale = 4.0`（`Save.Scale`），1:1 显示；即素材 1x 坐标 ×4 = 屏幕像素。

### 2.2 四类画面各自的路径

| 画面 | 取帧 | 渲染 | 备注 |
|---|---|---|---|
| 待机 | `assets/plain|superN/idle/<dir>/` PNG 帧序列（17 帧循环） | 预烘 PNG，直接 copy | 仅当前+上次方向常驻 |
| 动作 | `vecAnim`（每段动作一个渲染器） | worker 异步光栅化 → 位图 | 24fps，`tickMs=40` / `animFrameMs=41.67` |
| 表情 | 同上（`exps`） | 同上 | 计时随机触发 |
| 飞行器 | `flyCompositeFrames(style, dir, h, color)` 分层合成 | 预合成 PNG 帧 | 4 style，只画飞行器不叠本体 |
| 面板 | `panel_*.go` 各自 `uiWin` | 矢量按钮 + 位图 | 独立窗口 |

### 2.3 动作帧渲染的完整链路

```
tick(40ms) → draw()
  ├ setTint(玩家色)
  ├ currentFrame()
  │   └ FS.animFrame(kind, id, idx) → vecAnim.frame(idx)
  │        ├ buf[idx] 命中 → 直接返回（正常路径）
  │        ├ 未命中且 lastImg 非空 → 返回上一帧（画面停留，不阻塞）
  │        └ 未命中且无 lastImg → 返回 nil（draw 提前 return，窗口保留旧画面）
  ├ 算窗口尺寸/offX/offY（§1.2）
  ├ 裁到屏幕 → winX/winY/w/h
  ├ animSetVisible(-offX, -offY, w, h, …)   ← 告诉 worker 只渲这块
  ├ 需要时 newRenderer(w,h)
  ├ canvas = 新建 RGBA(w,h)
  ├ copyTo(canvas, frame, offX+FrameOff, offY+FrameOff)
  ├ 画气泡 / 芯片环 / 高光
  ├ tickGhost(canvas, g.BaseX, y)     ← 注意：这里用的是未裁剪坐标
  └ updateLayered(hwnd, R.Hdc, winX, winY, w, h)

vecAnim worker（min(3, NumCPU-1) 个）：
  loop：读 cur/vis → 找 cur-2 .. cur+12 里未渲染的帧 → RenderClip(rect = 帧bbox ∩ vis)
        → 写入 buf → 删除窗口外旧帧
```

### 2.4 可见区（vis）与求交

- `vis` = 窗口覆盖的 clip 范围，由 `(-offX, -offY, w, h) / a.scale` 得到，单位是素材 1x 坐标。
- `renderOne` 把 `frameRect(idx)`（帧 bbox，1x）与 `vis` 求交，**无交集直接返回 nil**（该帧在窗口外，不渲染）。
- 求交结果决定位图大小：常规动作帧 179×63；大特效帧 882×13 等。

**这条「求交」就是「框内才画」的执行点。**

## 3. 坐标系（一共 6 套，混用是这两天 bug 的主要来源）

| 名字 | 含义 | 单位 | 定义处 |
|---|---|---|---|
| `BaseX/BaseY` | 内容基准左上角（球心锚定的原点） | 屏幕像素 | 移动/拖动时更新 |
| `winX/winY` | **本帧窗口**的屏幕原点，含裁剪平移 | 屏幕像素 | `main.go:1004` |
| `WinX/WinY` | 命中判定用（= winX - AnimPad） | 屏幕像素 | `main.go:1128` |

| `FrameOff` | 帧 bbox 相对 clip 原点的偏移 ×scale | 屏幕像素 | `vecAnim.frame` 返回 |
| `BallSX/BallSY` | 球心屏幕坐标（快捷栏环心用） | 屏幕像素 | draw 后段 |

## 5. 已知问题（按严重度）

### 5.1 【已定位，未修】残影窗口与主窗口坐标不一致 → 本体「被横切」

- 代码：`main.go:1123` 传 `g.BaseX, y`；`main.go:1128` 主窗口用 `winX, winY`。
- 后果：凡是触发残影的超能形态，残影窗固定落在未裁剪位置，与主窗口错开 `(dx, dy)`（就是裁剪量）。视觉上本体的上下两半分别来自两个窗口，中间断开 —— 与图 2 一致。
- 影响面：只有 `SuperLevel > 0` 且发生位移（`|mdx|<=12`）时才 pushGhost；但残影窗口一直存在。
- 修法（一行级）：`tickGhost` 也传 `winX/winY`，并把 `prevBase*` 换成 `prevWin*`。**未动手。**

### 5.2 【未定位】切换形态后残影永远停在最后一帧

候选原因（无一是验证过的）：

1. `ghostBlockedByPanel()`（`panel_main.go:287`）若任一面板 `Visible` 卡在 true，`tickGhost` 每帧直接 return → `ghostPool` 的 `life` 永不递减 → 残影永久停留。
2. `hideGhostWindow()` 只清位图、保持窗口 mapped（注释说是为规避 Wine 的 `IsUnMapped`）。若清理时 `gw.X/Y` 与上次上传位置不一致，旧位置像素不会被擦除。
3. `applyForm()` 换形态时没有清理 `ghostPool`（只清 `g.Anim`/`Frame`），旧形态残影靠 `life` 自然过期（12 tick ≈ 0.5s）。若此时 draw 因别的原因提前 return，过期就不会发生。
4. 真机 layered window 的 `UpdateLayeredWindow` 传全透明位图后，桌面未触发重绘。

**要定位需要**：切换形态后抓 `ghost window created` / `resize` / `ghostBlockedByPanel` 相关日志。当前代码没有打印这条路径。

### 5.3 【未定位】真机卡顿

Wine 下动作期 tick 稳定 40.0ms，测不出卡。真机候选开销：

1. `renderGhostWindow()` 每 tick 调用，`blendTo` 是**逐像素** `RGBAAt/SetRGBA`（含 bounds 检查），520×520×2 层 ≈ 54 万次 ×2。
2. `renderGhostWindow` 每次整块清 520×520 再 blit。
3. 动作期间窗口 1280×1024 layered 全量上传（即使内容只占一小块）。
4. 200% DPI 下这些像素数 ×4。
5. `copyTo` 只拷实际内容矩形；`blit` 已按行跳过全透明行。

**要定位需要**：真机开 `NONO_PROF=1` 跑同一段动作，看 `PROF tick` / `PROF draw` / `PROF updateLayered` / `PROF blit` 各自耗时。

### 5.4 【已确认非 bug】`super2/action1` 只有 1 帧

矢量与 PNG 素材都只有一帧（`000.png`），原版即如此。

### 5.5 【未测】真实 Windows 全量表现

所有冒烟（42 段动作、9 段长动作、表情、飞行、6 形态球心、面板）都在 Wine 下通过，真机只靠你截图。

## 6. 为什么变成现在这样（演进代价表）

| 版本 | 做了什么 | 换来了 | 代价 |
|---|---|---|---|
| vec13 | 动作 4x 倍率统一 | 动作本体不缩小 | 单帧 408ms、内存 2.1GB |
| vec14 | 去掉整画布位图缓存，改「按帧 bbox 渲染 + 窗口随 bbox」 | 内存 2.1GB→129MB | **窗口随单帧 bbox 暴涨 3126×3961** → 这就是「框」的前身 |
| vec15 | 异步双缓冲、3 worker、窗口裁到屏幕 | 24fps 稳定、miss=0 | **框落进屏幕内，内容开始被切** |
| vec16 | 修可见区倍率（冻结 204 帧）、首帧异步 | 画面不再冻结 | **框的问题没解决，且新增残影坐标不一致** |

根子上的矛盾：

> **内容尺寸远大于屏幕**（super5/action_7 clip 3746×3648，屏幕 1280×1024），而「窗口 = 内容」会让窗口 3746×3648、每帧位图 54MB。
> 我选择了「窗口裁到屏幕 + 只渲染可见区」来保性能 —— 代价就是框。

## 7. 可选方向（只列权衡，不动代码）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 恢复大窗口** | 窗口 = 内容尺寸，不裁屏幕 | 无框、内容完整 | 窗口 3746×3648；DIB 每次 54MB；200% DPI 下更糟。vec13 实测单帧 408ms |
| **B. 大窗口 + 只上传可见子矩形** | 窗口按内容尺寸创建，但每帧只把屏幕内那块 blit 进 DIB，其余保持透明 | 无框（框在屏幕外）＋上传量小 | DIB 本身仍 54MB；`UpdateLayeredWindow` 每次要处理整窗位图（可只 blit 变化区） |
| **C. 主窗口 + 特效分窗** | 本体窗口贴本体，大特效另开穿透窗口 | 每个窗口都小 | 窗口数量增加，合成/层级/命中判定复杂度上升；多窗口对齐是新风险 |
| **D. DirectComposition / 无窗口渲染** | 用 DComp 视觉树直接贴屏 | 无窗口尺寸概念，真正「无框」 | 实现量大，需重写窗口层；兼容性待验 |
| **E. 维持现状，把框做成「不可见」** | 窗口始终 ≥ 屏幕，内容按屏幕对齐 | 改动最小 | 靠窗口覆盖屏幕规避视觉切割；本质仍是框 |

**我的判断**：B 最贴近你的要求（无框 + 不卡），实现集中在一个函数；D 是唯一真正根治的，但成本最高。C 我担心重蹈「多窗口错位」的覆辙（§5.1 就是这类问题）。
